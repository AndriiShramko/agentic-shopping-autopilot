# Execution stack: why browser agents are slow and how this project makes checkout fast

A general-purpose "LLM drives a browser" loop takes 8-20 minutes for one marketplace purchase in the project's current-baseline estimate ([hypothesis], not a measurement: estimated from the cited per-step latencies, which alone account for 3-10 minutes, plus retries and context compaction) and succeeds only about 30-60% of the time on live-site benchmarks. This page compares the browser-agent frameworks and MCP tools available in 2026, explains the technical causes of slowness and misses (token-heavy snapshots, per-step latency, unstable selectors, anti-bot), and describes the hybrid execution stack this project uses for autonomous checkout on Allegro and OLX: API-first search, deterministic recorded checkout flows stored as a site skill, and an LLM only at branches and breakages. Research date: 2026-08-31.

Evidence tags used below: **[fact]** = independent or verifiable source, **[vendor claim]** = self-reported by the tool's vendor, **[reported]** = a single secondary report or anecdote, not independently verified, **[hypothesis]** = the project's own inference.

## Questions this page answers

- Why is an AI shopping agent built on Claude Code (or Codex) plus a browser MCP so slow, and why does it miss?
- Which browser-agent framework (browser-use, Stagehand, Skyvern, Magnitude, Playwright MCP, Chrome DevTools MCP, Claude computer use) is fastest and cheapest for autonomous checkout?
- Can an AI agent buy on Allegro through the official API instead of a browser?
- How can an AI agent finish an Allegro or OLX purchase in 1-2 minutes instead of 10-20?

Related pages: [architecture.md](architecture.md) (overall design), [site-skill-spec.md](site-skill-spec.md) (how recorded flows and selector caches are packaged), [anti-bot-policy.md](anti-bot-policy.md) (what the project never does), [payments.md](payments.md) (PSD2 / SCA / 3DS), [mandate-spec.md](mandate-spec.md) (the purchase mandate that bounds every run).

## 0. The main caveat about benchmark numbers

- **[fact]** (arXiv 2504.01382, "An Illusion of Progress?", OSU + UC Berkeley, April 2025): the classic WebVoyager benchmark systematically overstates results. On the live Online-Mind2Web benchmark (300 tasks, 136 real websites) the success rate of state-of-the-art agents drops from ~90% to **~30%**; the best result was OpenAI Operator at **61%**. The automatic judge (WebJudge) agrees with humans 85.7% of the time.
- **[fact]** (github.com/nottelabs/open-operator-evals, 2025): the 89% claimed by browser-use did not reproduce; an independent run gave **77.3% self-reported / 60.2% LLM-verified**.
- Consequence: the WebVoyager numbers in the tables below are comparable **only with each other**. A real "buy this on Allegro" task is closer to Online-Mind2Web / REAL than to WebVoyager.

## 2. Why "Claude Code + browser" is slow and misses

[hypothesis] The same causes apply to Codex or any other coding agent driving a browser through MCP; Claude Code is used as the concrete example because it is the project's default harness.

### 2.1. Technical causes

1. **Screenshots are expensive only when they are handled badly, and then catastrophically.**
   - [fact] (Anthropic vision documentation; OpenAI image-input documentation; source 21): a natively encoded screenshot costs on the order of 1-2k tokens per image at standard settings. Anthropic bills visual tokens by 28x28-pixel patches, capped at 1,568 tokens per image on standard-tier models (up to 4,784 on high-resolution models); OpenAI's per-tile or per-patch pricing puts a 1024x1024 image at a few hundred to about 1.2k tokens.
   - [reported] (Medium, May 2026, single anecdote, source 17): a single screenshot call in a Playwright MCP session inflated the context to **232,000 tokens**. That is the pathological case in which the MCP client returns the image as base64 text, not the normal cost of a screenshot.
   - [hypothesis] The catastrophe happens when (a) an MCP client returns the screenshot as base64 text, or (b) a screenshot is returned on every step and stays in the history. The often-quoted comparison "a few KB of a11y text versus 100 KB+ for a PNG of the same page" is a difference in bytes, not in tokens. The real advantage of a11y snapshots is actionable element references and diffability, not raw token count.
2. **The accessibility tree is better, but still fat, and it accumulates.**
   - [fact] (dev.to browser-MCP measurement, source 17: Playwright MCP snapshots of the Wikipedia, GitHub and Hacker News pages measure 58-78k characters, i.e. 14.5-19.4k tokens; paddo.dev "The Context Wars", source 17): on a real production page the a11y snapshot is **50-100 KB**, i.e. roughly 12-25k tokens; every snapshot **stays in the conversation history**, so 10 steps x 50 KB is about half the context. Separately, the tool definitions of a browser MCP are themselves large: about **15,000 tokens** for Playwright MCP (research estimate) and **~17,000** for Chrome DevTools MCP (paddo.dev, source 17).
   - [hypothesis] (consistent with the project's experience): Allegro pages (listings with hundreds of offers, banners, consent popups) produce a11y snapshots at the upper end of that range; 2-4 listing steps eat the context, compaction starts, and the agent "forgets" what it has already seen.
3. **Re-reading the same pages.** An agent with no memory of the site reads a fresh snapshot of the same page after every click (a snapshot comes back on every action). A frame is not a diff: MCP does not return "what changed", it returns everything. [fact] by design of Playwright MCP / Chrome DevTools MCP (docs); the amplification is the project's inference.
4. **Loop latency.** [fact] (arXiv 2605.16565 "Skim: Speculative Execution for Web Agents", 2026): median **4.7 s of LLM inference + 6.6 s of browser action** per step; WebVoyager tasks take from 29 s to **1,370 s (~23 min)**. A typical purchase is 15-40 steps, i.e. 3-10+ minutes of pure loop time.
5. **Misses.** Causes per the literature ([fact]: arXiv 2504.01382; WebSight, arXiv 2508.16987): unstable selectors / element indices between snapshots, dynamic DOM (Allegro is an SPA with lazy loading), consent / cookie popups, iframes, and anti-bot systems (Allegro is protected by **DataDome**: [vendor claim], DataDome customer story, 2024, source 23).

### 2.2. Techniques that speed things up several-fold (with real measurements)

| Technique | Measured effect | Source, evidence type |
|---|---|---|
| **Selector cache / recorded actions** (Stagehand observe->act cache + self-healing) | replay with no LLM at all; "up to 10x fewer tokens" when the selector is passed into extract | [fact] per docs.stagehand.dev/examples/caching; browserbase.com/blog/stagehand-caching [vendor claim] |
| **Deterministic replay of an entire flow** (Skyvern Code Caching) | **279 s -> 120 s (2.3x), $0.11 -> $0.04 (2.7x), -90% tokens**; on breakage, automatic fallback to the agent | [vendor claim] with concrete numbers (skyvern.com/docs/developers/features/code-caching, 2026) |
| **Deterministic rerun** (browser-use cloud) | replay from a cached script "instantly, up to 99% cheaper" | [vendor claim] (docs.browser-use.com/cloud/agent/cache-script) |
| **Recorded workflows + variables** (browser-use/workflow-use, "RPA 2.0") | record once -> deterministic run, LLM only as a fallback on a failed step | [fact] that it exists (github.com/browser-use/workflow-use); status "early development" |
| **Official search API instead of browser navigation** (Layer 1 in section 3) | one HTTP call per query instead of a multi-step browser loop; no navigation misses; more robust to redesigns | [fact] that the Allegro offer-search API exists (developer.allegro.pl, source 22); the size of the speed-up is a [hypothesis], project estimate |
| **Compact snapshots** (agent-browser: semantic references to elements) | "-93% context": 200-400 tokens per snapshot versus ~15k tokens for a full Playwright MCP snapshot of the same page | [vendor claim] (paddo.dev / betterwright.com, 2026) |
| **Site-specific skills** (Anthropic Agent Skills, an open standard since 2025-12-18; Claude in Chrome GA 2026-08-26, see section 1.2) | a skill is a recorded instruction "how to walk this site" -> fewer exploratory steps | [fact] for the releases (venturebeat.com; source 13 for Claude in Chrome); the size of the effect is a [hypothesis] |
| **Vision grounding only at branches** (the Magnitude approach) | fewer misses on non-standard widgets (price sliders and the like) | [vendor claim] (magnitudedev) |

**The key industry pattern of 2026** ([fact]: Skyvern, browser-use and Stagehand converge on it): the agent explores a site **once**, compiles a deterministic script, and from then on the LLM is touched only at branches and breakages. That is exactly "hybrid: API where possible, browser where not, cache where stable", and it is what agent skills (a site skill per marketplace) package for this project.

### 2.3. Allegro / OLX specifics

- **[fact]** (developer.allegro.pl): Allegro has an official REST API with OAuth. Searching and viewing offers is available through the API; orders (`/order/checkout-forms`) are on the seller side. The bidding endpoint `PUT /bidding/offers/{offerId}/bid` exists, but in March 2026 developers were getting "Funkcja niedostępna" (github.com/allegro/allegro-api/issues/13148). Buying via "Kup teraz" through the public API is **not supported**. Consequence: search and comparison go through the API, checkout only through the browser.
- **[vendor claim]** (datadome.co customer story, 2024, source 23): Allegro is protected by DataDome. Independently of any detection system, the project's policy is that checkout runs only in the **user's own logged-in Chrome profile on the user's own machine** (CDP / Chrome DevTools MCP / extension): that is where the user's session and saved payment methods live, and it is the posture [anti-bot-policy.md](anti-bot-policy.md) commits to. Headless and cloud browsers are out of scope for the MVP (see the grey/black tiers in [anti-bot-policy.md](anti-bot-policy.md)). The project does not attempt to defeat any platform control; any CAPTCHA or anti-bot challenge is handed to the user.
- **[fact]** (developer.olx.pl): the OLX Partner API covers posting / managing listings and messages; there is no buyer checkout in the API. An OLX deal often means chatting with the seller. Project scope for the MVP: only the native escrow flow "Kup z Przesyłką OLX"; a chat / negotiation module is v2, with human escalation. Search runs through the browser via the site skill; any use of non-public endpoints is out of scope pending a terms review (see [marketplaces.md](marketplaces.md)).

## 3. The recommended execution stack for the MVP

1. **Layer 1: API-first (no browser).** Product search and filtering: the official Allegro REST API (offer search), seconds per query and no navigation misses ([fact]: the API exists; the choice is a recommendation). For OLX there is no buyer search API; the MVP searches through the browser via the OLX site skill. Whether any non-public endpoint may ever be used is deferred until OLX's terms are reviewed (see [marketplaces.md](marketplaces.md)); none is used or documented here.
2. **Layer 2: deterministic recorded checkout flows.** Playwright scripts "add to cart -> delivery -> payment", recorded once on the live site and stored as a site skill (selectors + steps + checkpoints; see [site-skill-spec.md](site-skill-spec.md) and the reference skill [../skills/allegro.pl/](../skills/allegro.pl/): [SKILL.md](../skills/allegro.pl/SKILL.md), [selectors.yaml](../skills/allegro.pl/selectors.yaml), [flows/](../skills/allegro.pl/flows/)). Execution is estimated at 30-90 s with no LLM (project estimate; see the target-time table below). The pattern is backed by Skyvern's numbers (2.3x faster, -90% tokens) and Stagehand's cache. The flow ends on the marketplace's own pay button ("Kupuję i płacę" on Allegro), which the agent presses itself inside the purchase mandate. Allegro's Terms (Regulamin, edition effective 2026-09-01, read 2026-09-03; source 27) prohibit the use of bots and other software tools while using Allegro (art. 10.11) and scraping of its data for reuse (art. 10.10), and state that automated solutions are used at the user's own risk (art. 2.8); secondary reports describe this as a ban on automated ordering, and Allegro publishes no buyer purchase API. An agent driving the user's own browser may fall under art. 10.11; how the project handles that is stated in item 4 below and in [marketplaces.md](marketplaces.md) and [anti-bot-policy.md](anti-bot-policy.md).
3. **Layer 3: LLM only at branches.** Claude (Sonnet 4.6 class) through **Chrome DevTools MCP against the user's real Chrome profile** (existing logins, no headless cloud), with a11y snapshots, NOT screenshots. It is switched on when a selector fails, an unfamiliar popup appears, a choice between product variants is needed, or the total has to be checked against the mandate. Self-healing: the LLM repairs the step and updates the cache (as in Stagehand / Skyvern). All layers attach to the same user Chrome instance over CDP (Playwright `connectOverCDP` / Chrome DevTools MCP); frameworks that launch their own browser are used only in CDP-attach mode.
4. **Payment and autonomy: project decisions.** The default is autonomous: the agent completes checkout and presses pay inside the limits of the [purchase mandate](../examples/PURCHASE_MANDATE.template.md), using the payment methods already saved in the user's marketplace account (one-click saved card via PayU and/or Allegro Pay). A human is involved only for the bank's own 3DS / SMS challenge (PSD2 SCA, unavoidable; see [payments.md](payments.md)), a CAPTCHA / anti-bot challenge, or any deviation from the mandate. A "human confirms payment" mode exists as an optional config flag, not the default. Anthropic's computer-use documentation recommends asking a human to confirm decisions such as completing financial transactions (section 1.2, source 26). The project's default deliberately departs from per-purchase confirmation: it treats the signed purchase mandate (limits, written, revocable; see [mandate-spec.md](mandate-spec.md)) as advance consent, and the human-confirm flag restores per-purchase confirmation for users who want the recommended behaviour. Marketplace terms: Allegro's Terms (Regulamin, edition effective 2026-09-01, read 2026-09-03; source 27) prohibit the use of bots and other software tools while using Allegro (art. 10.11) and scraping of its data for reuse (art. 10.10), and state that automated solutions are used at the user's own risk (art. 2.8); secondary reports describe this as a ban on automated ordering; Allegro publishes no buyer purchase API. An AI agent driving the user's own browser may fall under art. 10.11. The project does not disguise the agent and does not attempt to defeat any platform control: the default completes payment inside the mandate, the human-confirm flag is available, and each account holder decides and accepts the risk for their own account. The agent drives one interactive browser, one action at a time, and the number of purchases per day is bounded by the mandate. See [anti-bot-policy.md](anti-bot-policy.md) and [marketplaces.md](marketplaces.md). The prompt-injection figures above (attack success rate 11.2% after mitigations, [fact]) are why the project treats page content as data, never as instructions, keeps card data, cookies and OTP codes out of the LLM context entirely, and writes every action to an append-only audit log (see [security.md](security.md)).
5. **Framework candidates for layers 2-3:** **Stagehand** (MIT, TS/Python, cache + self-healing, local browser) or **browser-use + workflow-use** (Python, cheap BYOK mode). Skyvern is an architecture reference (AGPL; be careful with the license). Nova Act means AWS vendor lock-in; Magnitude is the fallback for vision-heavy branches. See [landscape.md](landscape.md) for the wider agentic-commerce landscape and [registry.md](registry.md) for how skills are published.

**Target time for "find and buy an item on Allegro":**

| Setup | Time | Success | Evidence |
|---|---|---|---|
| Naive baseline today (Claude Code + Playwright MCP, screenshot or full-snapshot loop) | **8-20 minutes** ([hypothesis], the project's current-baseline estimate, not a measurement) | ~30-60% | success anchored in [fact]: Online-Mind2Web ~30-61%; time: Skim per-step latencies give 3-10 minutes of loop time, the rest is retries and context compaction |
| MVP hybrid stack, first (cold) run of a new flow | **4-6 minutes** | - | [hypothesis], conservative |
| MVP hybrid stack, repeat purchase on a cached flow | **1-2 minutes** (API search <10 s, checkout replay 30-90 s, LLM checks 30-60 s) | - | [hypothesis]: Skyvern's 120 s figure is for a full cached task; here search is done via the API, so the replayed checkout is a shorter flow and 30-90 s is the project's estimate, not a measurement; the API layer's speed-up (one HTTP call per query instead of a multi-step browser loop) is likewise a project estimate |

The first and most important MVP metric is not speed but the field-measured frequency of bank challenges (3DS / SMS) on the saved card or Allegro Pay at small amounts: it determines the real share of purchases that need zero human involvement. The project never attempts to avoid, suppress or influence whether SCA fires; that decision (including any low-value or TRA exemption) belongs to the issuer and acquirer. The metric only sizes the share of purchases that will need a human step.
